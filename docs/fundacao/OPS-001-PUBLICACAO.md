# OPS-001 — Publicação do staging compartilhado

09/11/2026. Próximo recorte após INT-003, autorizado pelo prosseguimento da responsável. RNF-002/003/008/011/015; View/Controller/Service/Repository já verificados são preservados. Meta de [10/11](../planejamento/PLANO-ATE-10-11.md) prioriza publicação e [primeiro fluxo de estoque](EST-001-PRIMEIRO-FLUXO.md), não o ERP integral.

## Desenho

Um Worker `erp-joinville-staging` serve o build de apps/web e a API no mesmo endereço. [Configuração](../../wrangler.staging.jsonc) aponta exclusivamente apps/web/dist como diretório público; nenhuma pasta do repositório, arquivo privado ou legado é publicado como asset. `/api` e `/api/*` executam o Controller antes do fallback SPA, mantendo erros HTTP JSON. Outros caminhos servem os assets/SPA. Isso elimina configuração CORS entre View/API e usa o mesmo Supabase existente. Nenhum ambiente permanente adicional; AMB-001 permanece congelada.

Previews versionadas e observabilidade com captura de requisições estão desabilitadas. Não registrar Authorization, senha, corpo de login ou dados privados em logs/evidências. Headers de segurança/noindex estão no wrapper API e `_headers` dos assets; não são substituto de autenticação/RLS. O login fica acessível, operações exigem Bearer/perfil/vínculo; staging continua restrito a dados sintéticos.

Somente SUPABASE_URL e SUPABASE_PUBLISHABLE_KEY são necessários no Worker; VITE_SUPABASE_URL/VITE_SUPABASE_PUBLISHABLE_KEY no build da View. Nunca service_role/sb_secret, senha, JWT ou token de deploy no bundle. O arquivo privado de runtime passado por `--secrets-file` contém apenas essas duas variáveis públicas; não passar o arquivo de identidades ou a resposta api-keys --reveal.

## Procedimento verificável

1. Conferir git limpo/commit e CI, build com URL/chave públicas do projeto existente. `npm run build:staging` é dry-run e não publica. Build comum do CI também valida a configuração integrada.
2. Autenticar Wrangler na conta confirmada da responsável; inventariar o nome antes de publicar, sem sobrescrever outro projeto ou contratar plano. Login OAuth inicial por callback expirou; fluxo por dispositivo concluiu com sucesso. Credenciais ficam no perfil local do Wrangler, fora do repositório. Nenhum token deve ser copiado ao chat/PR.
3. Publicar `npm run deploy:staging -- --secrets-file <arquivo-runtime-privado.json>` ou executar Wrangler diretamente com a configuração raiz após build. Registrar commit/versão/URL e variáveis por nome, sem conteúdo privado. Não habilitar produtos pagos, domínio ou outro ambiente por inferência.
4. Verificar HTTPS, HTML/assets, /api/health, API desconhecida 404 JSON, acesso sem Bearer 401 e headers. Executar login/consulta/edição/revisão/retorno e isolamento no endereço hospedado, sem mocks; conferir auditoria remotamente por consulta controlada.
5. Acrescentar resultados efetivos e limitações. CI/merge não comprovam deploy e health não comprova banco/Auth. Preservar credenciais e capturas de login fora do checkout.

Se houver versão anterior deste mesmo Worker, anotar a versão antes do upload e usar rollback oficial caso necessário. Na primeira publicação, retorno é retirar o acesso público do Worker específico se o smoke falhar, sem apagar banco ou identidades. Não executar rollback/reset do Supabase como procedimento de publicação.

Fontes oficiais consultadas: [Workers Static Assets](https://developers.cloudflare.com/workers/static-assets/), [roteamento seletivo](https://developers.cloudflare.com/workers/static-assets/routing/worker-script/) e [headers](https://developers.cloudflare.com/workers/static-assets/headers/). A separação MVC do código continua vigente mesmo com um único ponto de publicação.

## Resultado

**Publicado e verificado em 10/11:** https://erp-joinville-staging.erp-restaurantes-joinville.workers.dev. Runtime final do commit `31bfcf626b655fa3a9f91bd1f4cda3be5285d8a4`, versão Cloudflare `66a6571d-a228-41cf-9c6b-88125818e0af`. CI [42821040613](https://github.com/larabeatrizs/ERP_Restaurantes_Joinville/actions/runs/42821040613) aprovou os quatro jobs antes da republicação. [Metadados/pós-condições](../evidencias/ops-001/publicacao.json) e [jornada hospedada](../evidencias/ops-001/jornada-hospedada.json).

O login confirmado no terminal incluiu workers_scripts:write; o inventário passou do 403 anterior para Worker inexistente 10007. A primeira publicação, commit 34bdd98/versão `85036627-8410-4de5-9ed9-c63708507eea`, registrou o subdomínio workers.dev da conta e criou somente este Worker de staging, com assets, URL/chave publicáveis. HTTPS ficou disponível após propagação inicial de aproximadamente três minutos, sem desabilitar TLS. Não houve plano pago, conta temporária, outro projeto Supabase ou ambiente permanente adicional.

Smoke final: HTTPS e HTML/JS/CSS 200, health 200, API inexistente 404 JSON, falta de Bearer 401, headers nosniff/DENY/no-referrer/noindex. As rotas autenticadas continuam no-store. Browser e SDK reais confirmaram login, editor de configurações revisa/salva/restaura e leitor só consulta; verificações HTTP adicionais negaram PATCH do leitor (403), GET de unidade não vinculada (404), PATCH cruzado (403) e anon (401).

O primeiro teste de configurações não foi aceito: resposta 200 com Brotli transformava `"cfg-1-8"` em `W/"cfg-1-8"`, e a View corretamente rejeitava ETag fraca. A mesma leitura com Accept-Encoding identity preservava ETag forte; não houve escrita nessa tentativa. A correção adicionou `Cache-Control: no-store, no-transform` às respostas versionadas de configurações/produtos. Depois da republicação, uma leitura pedindo gzip/br preservou ETag forte; o teste de salvar/restaurar passou. If-Match, revisão, autenticação e RLS não foram relaxados. [Compressão Cloudflare](https://developers.cloudflare.com/speed/optimization/content/compression/), [ETags](https://developers.cloudflare.com/cache/reference/etag-headers/).

Estoque hospedado: seis cenários HTTP e cinco fluxos UI completos sem mocks. Produto cadastrado/buscado/editado; compra de 20 kg confirma uma vez, lote/local/saldo conferem; nova sessão recupera registros; leitor/outra unidade/DML direto e NF duplicada são negados. Desktop e 360 px foram conferidos, com colunas legíveis e rolagem por teclado. A captura de produtos foi refeita somente por consulta após a busca terminar, e o verificador passou a aguardar a resposta de rede para evitar registrar o estado de carregamento. Capturas: [configurações](../evidencias/ops-001/configuracoes-hospedadas-1280.png), [produtos](../evidencias/ops-001/produtos-hospedados-1280.png), [recebimento](../evidencias/ops-001/recebimento-hospedado-1280.png), [saldo móvel](../evidencias/ops-001/saldo-hospedado-360.png), [consulta móvel](../evidencias/ops-001/consulta-hospedada-360.png).

Pós-condições acumuladas das rodadas locais/hospedadas: seis produtos/entradas confirmadas/lotes/movimentos, todos os saldos de demonstração em 20 kg, 21 eventos de estoque e zero eventos do leitor, nenhuma divergência livro/saldo ou saldo da unidade B. Configurações retornaram a 5,00/POSTERIOR, revisão A=10/B=1, 11 eventos de configuração; nenhuma trilha apagada. Permanecem quatro migrations, 20 tabelas erp com RLS e executor sem USAGE auth. Credenciais/capturas originais ficam fora do checkout; somente evidência sanitizada publicada.

A meta técnica do primeiro fluxo online foi atendida antes de 11/11. Não encerra D1, RF-008 integral, RNF-004, FND_READY ou aceite institucional. Advisor mantém 14 INFO do legado intencionalmente contido e WARN de [senhas vazadas](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection), a revisar antes de uso real. AMB-001 permanece congelada; próxima frente são os cadastros/contratos restantes da D1. A versão inicial mantém a limitação de ETag documentada; um eventual rollback deve considerar essa diferença e não reverter o banco por inferência.
